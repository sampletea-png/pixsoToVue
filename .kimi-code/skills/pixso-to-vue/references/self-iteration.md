# Skill 自我迭代协议

本 skill 假定自己**不可能一次写对**。每次运行结束（Phase 9）必须执行本协议，把运行中暴露的问题转化为 skill 的改进。

## 第 1 步：复盘日志

在仓库 `iterations/` 新建 `YYYY-MM-DD-<主题>.md`（格式见 `iterations/README.md`），如实记录：

- 哪个阶段出现了失真 / 误判 / 返工；
- 根因（是 AI 判断失误，还是脚本缺陷，还是规则文档缺失）；
- 当时怎么修的。

不隐瞒失败。日志是后续迭代的唯一依据。

## 第 2 步：修订建议（严格按优先级）

**优先级 1 — 脚本化**：凡是"机械但 AI 又做错了/做得不一致"的环节，新增或增强 `scripts/` 下的脚本。
例：AI 手写的某种转换每次都漏 → 写成脚本；某类 MCP 载荷解析出错 → 修 `mcp_call.py` 或对应采集脚本。

**优先级 2 — 规则修订**：推断类错误，修订 `references/` 对应规则文档（补充对照表行、修正判断纪律），必须写明改哪条、为什么。

**优先级 3 — 流程修订**：阶段划分/门禁本身有问题，才改 `SKILL.md`。

**反模式（禁止）**：

- 只在文档里加"下次注意"而不动脚本/规则；
- 为单次特例加全局规则（先确认该问题会复现）；
- 未经用户确认直接改 skill。

## 第 3 步：应用与版本

- 修订建议逐条经用户确认后应用。
- 应用后递增 `SKILL.md` frontmatter 的 `version`（规则/脚本修订 +0.1.0，流程修订 +1.0.0 并重置小版本）。
- 在当日日志「已应用的修订」一节记录：改了哪些文件、version 从多少变为多少、原因。

## 第 4 步：验证（下一轮运行时）

下一篇迭代日志开头先回顾：上一轮的修订本次是否生效？未生效的修订要重新评估（是修订本身错了，还是没执行到位）。
